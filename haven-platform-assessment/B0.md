# B0 - The `count` trap

(Written from reasoning about the seeded state and config; Terraform wasn't available in my
environment, so reproduce with `terraform plan -refresh=false` after removing "la-002".)

## What `terraform plan` shows

`count` addresses instances by **position**. State holds `landlord_media[0..3]` =
la-001, la-002, la-003, la-004. Removing "la-002" gives the list `[la-001, la-003, la-004]`:

| Address | State has | Config now wants | Result |
|---|---|---|---|
| `[0]` | haven-media-la-001 | haven-media-la-001 | no change |
| `[1]` | haven-media-la-002 | haven-media-la-003 | `bucket` is ForceNew -> **replace** (destroy + create) |
| `[2]` | haven-media-la-003 | haven-media-la-004 | **replace** |
| `[3]` | haven-media-la-004 | (gone) | **destroy** |

Roughly: `Plan: 2 to add, 0 to change, 3 to destroy.` The operator meant to remove one landlord
and the plan touches three buckets - including the two landlords that were **not** removed.

## Why it is dangerous here

- It's the wrong buckets being destroyed. la-003 and la-004 are live customers; their media
  buckets are slated for deletion even though only la-002 left. la-002's bucket is "replaced" by
  one named for la-003.
- S3 bucket names are globally unique. `[1]` wants to create `haven-media-la-003`, which already
  exists as `[2]` - so the apply fails or races partway, leaving state half-migrated.
- If the buckets are non-empty, deletion fails (safe by accident). If anyone has `force_destroy
  = true` or empties them to "get the apply through", it is permanent loss of landlords' media.
- Tags: the billing tag `landlord_account_id` is rewritten on shifted instances, so cost
  attribution breaks during the churn.

Root cause: the list index is not the identity. The identity is the landlord account id.

## The fix

1. Key the resource by the landlord id with `for_each`:

   ```hcl
   resource "aws_s3_bucket" "landlord_media" {
     for_each = toset(var.landlord_accounts)
     bucket   = "haven-media-${each.key}"
     tags     = { landlord_account_id = each.key }
   }
   ```

2. Migrate state **before** removing anyone, so it's a no-op rename rather than a rebuild:

   ```hcl
   moved { from = aws_s3_bucket.landlord_media[0]  to = aws_s3_bucket.landlord_media["la-001"] }
   moved { from = aws_s3_bucket.landlord_media[1]  to = aws_s3_bucket.landlord_media["la-002"] }
   moved { from = aws_s3_bucket.landlord_media[2]  to = aws_s3_bucket.landlord_media["la-003"] }
   moved { from = aws_s3_bucket.landlord_media[3]  to = aws_s3_bucket.landlord_media["la-004"] }
   ```

   (or `terraform state mv` for each). Confirm `terraform plan` shows "0 to add, 0 to destroy".
3. Now removing "la-002" plans exactly one destroy: `landlord_media["la-002"]`.
4. Guardrails: `lifecycle { prevent_destroy = true }` on the media bucket (offboarding becomes a
   deliberate, reviewed change), versioning/backups, and a CI check that fails any plan that
   destroys or replaces more buckets than intended.
